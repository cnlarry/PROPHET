## 根本原因分析

### 🔴 致命问题1：所有权混乱

**位置**: `Prophet.Core/bindings/python_bindings.cpp:393-417`

```cpp
// ❌ 错误：将裸指针包装进unique_ptr，违反RAII
std::vector<std::unique_ptr<Engine>> engines;
for (auto item : engines_list) {
    auto* engine_ptr = item.cast<Engine*>();
    engines.push_back(std::unique_ptr<Engine>(engine_ptr)); // 假装拥有
}

// ... 中间使用 ...

// ❌ 错误：又放弃所有权
for (auto& engine : engines) {
    engine.release(); // 潜在的内存泄漏/悬空指针
}
```

**后果**：
- 违反C++ RAII原则
- 潜在的内存安全问题
- 编译器无法优化（混乱的所有权语义）
- **每次调用都要重新构造unique_ptr向量（巨大开销）**

---

### 🔴 致命问题2：线程不安全

**位置**: `Prophet.Core/src/strategy/batch_engine.cpp:92-106`

```cpp
for (size_t i = 0; i < total_tasks; ++i) {
    futures.push_back(std::async(std::launch::async, 
        [&engines, &klines, current_price, current_time, i]() -> Signal {
            // ❌ 问题：多个线程访问同一个Engine实例
            engines[i]->SetKlines(...); // Engine不是线程安全的！
            return engines[i]->getSignal(current_price, current_time);
        }
    ));
}
```

**问题**：
1. **Engine不是线程安全的**：
   - `Context` 有可变状态
   - `IndicatorCache` 使用`std::unordered_map`（非线程安全）
   - `SessionCache` 也不是线程安全的

2. **多个线程同时修改同一个Engine**：
   - `SetKlines()` 修改内部状态
   - `getSignal()` 调用时可能发生数据竞争

---

### 🔴 致命问题3：std::async性能陷阱

**性能测试**（16个策略）：
```
创建16个std::async任务的开销 >> 实际计算时间
```

**问题**：
1. **线程创建开销**：
   - 每次调用创建16个新线程
   - 线程创建时间：~10-50μs/线程
   - 16线程 = ~160-800μs **仅创建开销**

2. **线程调度开销**：
   - 16个策略在16核上调度
   - 但每个策略只需要~30μs计算
   - 调度开销 > 计算时间！

3. **没有线程池复用**：
   - 应该使用线程池
   - 现在每次都创建/销毁

---

### 🔴 致命问题4：不必要的SetKlines调用

**位置**: `batch_engine.cpp:96-100`

```cpp
// ❌ 问题：每个线程中都重新SetKlines
engines[i]->SetKlines(
    klines.open, klines.high, klines.low, klines.close,
    klines.volume, klines.open_time, klines.close_time,
    klines.count
);
```

**后果**：
- K线数据本应在外部设置一次
- 现在每次评估都重新设置
- 增加了16倍的`SetKlines`调用（16个策略）
- 每次`SetKlines`可能触发缓存失效

## 性能计算

### 理论计算（16策略，16线程）

**期望**：
- 单策略计算时间：~30μs
- 16策略串行：16 × 30μs = 480μs
- 16策略并行（理想）：30μs（完美并行）
- **期望加速比：16x**

**实际**：
- 16策略串行：1,143μs (应该是480μs)
- 16策略Batch串行：4,615μs (应该是480μs)
- 16策略Batch并行：2,258μs (应该是30μs)

**开销分解**：
1. Python绑定开销：~1,143μs - 480μs = **663μs**
2. unique_ptr包装开销：~4,615μs - 1,143μs = **3,472μs**
3. 线程创建/调度开销：~2,258μs - 480μs = **1,778μs**

## 解决方案

### 方案A：修复当前设计（推荐）

1. **修复Python绑定**：
   ```cpp
   // ✅ 正确：使用裸指针，避免所有权转移
   std::vector<Engine*> engines_raw;
   for (auto item : engines_list) {
       engines_raw.push_back(item.cast<Engine*>());
   }
   ```

2. **确保线程安全**：
   - 在Python端提前调用`SetKlines`
   - 在C++端移除`SetKlines`调用
   - 确保每个Engine独立（不共享可变状态）

3. **使用真正的线程池**：
   - 替换`std::async`为线程池
   - 预创建线程，重复使用
   - 批量分发任务，减少同步开销

### 方案B：重新设计API（最优但工作量大）

1. **BatchEngine持有Engine实例**：
   ```cpp
   class BatchEngine {
       std::vector<std::unique_ptr<Engine>> engines_;
       std::vector<std::thread> thread_pool_;
       // ...
   };
   ```

2. **预先克隆Engine**：
   ```cpp
   void addEngine(const Engine& engine_template) {
       engines_.push_back(engine_template.clone());
   }
   ```

3. **持久化线程池**：
   - 构造时创建线程池
   - 使用任务队列
   - 避免重复创建/销毁
