## 当前瓶颈分析

### 问题1：std::async的巨大开销

**实验数据**：
- 16策略 × 50轮 = 800次`std::async`调用
- 每次创建16个线程
- **总线程创建：12,800个线程**

**开销估算**：
```
线程创建时间：~10-50μs/线程
12,800线程 × 30μs = 384,000μs = 384ms

总测试时间：50轮 × 375μs = 18.75ms（测量值）
线程创建占比：384ms / 18.75ms = **线程创建时间超过计算时间20倍！**
```

### 问题2：任务粒度太细

**单策略计算时间**：
```
26,756 ops/s ÷ 16策略 = 1,672 ops/s/策略
1 / 1,672 = 0.598ms = 598μs / 16 = ~37μs/策略
```

**结论**：
- 单个策略只需要**37微秒**
- 线程创建+调度：**10-50微秒**
- **线程开销 ≈ 计算时间！**

这就是为什么加速比只有1.59x的根本原因。

### 问题3：GIL仍然存在

即使在C++中使用`std::async`，Python的GIL在某些关键路径上仍然可能造成影响：
- `Signal`对象的创建（可能涉及Python对象）
- 结果向量的返回（Python绑定层）

## 解决方案

### 方案A：实现线程池（P1优化）

**目标**：消除重复的线程创建开销

```cpp
class BatchEngine {
private:
    std::vector<std::thread> thread_pool_;
    std::queue<Task> task_queue_;
    std::mutex queue_mutex_;
    std::condition_variable cv_;
    
public:
    void initThreadPool(size_t num_threads) {
        for (size_t i = 0; i < num_threads; ++i) {
            thread_pool_.emplace_back([this]() {
                while (true) {
                    Task task = getNextTask();
                    if (task.is_exit()) break;
                    task.execute();
                }
            });
        }
    }
};
```

**预期提升**：
- 消除384ms的线程创建开销
- 预期加速比：**8-12x** (当前1.59x)
- 预期吞吐量：**200,000-300,000 ops/s**
