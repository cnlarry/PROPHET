## 📝 Claude 审查结果（2026-01-01）

### 🔴 致命缺陷（可能导致项目失败）

#### 1. 回测时间语义严重模糊

PRD中最致命的问题是**没有区分"事件发生时间"和"信号可查询时间"**。

```cpp
// PRD中的设计
double GetIntelligenceStrength(
    string category, 
    string symbol, 
    int lookback_seconds,
    DateTime? backtest_time = null  // ❌ 可选参数是灾难
)
```

**问题链条**：
1. `backtest_time` 是可选参数，默认使用 `DateTime.Now`
2. 如果策略开发者忘记传入，回测时会使用当前时间 → **100%未来函数**
3. PRD没有说明回测引擎如何自动注入正确的时间 → **责任不明确**

**真实场景**：
```
09:00 - BTC暴跌5%，新闻事件发生
09:05 - 实时池采集到资金费率异常
09:30 - 趋势池启动批处理
10:00 - LLM分析完成，生成信号 (timestamp = 10:00)
```

**问题**：回测时 09:15 的K线bar能看到这个信号吗？
- 按PRD设计：查询 `timestamp <= 09:15`，看不到（timestamp=10:00）
- 但用户预期：09:00已经暴跌了，我9:15应该能收到信号！

**这导致回测结果与实盘完全不可比**。

#### 2. 历史数据空洞完全没有处理

PRD **完全没有讨论**：如果用户回测2024年策略，但情报数据只有2025年的，会发生什么？

```csharp
// 用户在DSL中写
if (GetIntelligenceStrength("funding_extreme", "BTCUSDT", 3600) < -50) {
    Buy();
}
```

**回测2024年时会发生什么？**
- 返回0？→ 用户误以为"2024年从来没有极端资金费率"
- 返回null？→ 策略报错崩溃
- 抛异常？→ 用户体验灾难

**这会导致用户做出错误的策略决策**。

#### 3. LLM输出稳定性被严重低估

PRD要求LLM输出复杂JSON：

```json
{
  "signals": [
    {
      "symbol": "BTCUSDT",
      "strength": -68,     // 必须是-100到+100的数值
      "confidence": 0.78,  // 必须是0-1的小数
      "urgency": "high",   // 必须是枚举值
      ...
    }
  ]
}
```

**实际问题**：
1. Gemini经常在JSON前后加 ` ```json ` 代码块
2. LLM可能输出 `strength: "very high"` 而不是数值
3. `urgency` 可能输出 `"urgent"` 而不是 `"high"`
4. 复杂嵌套结构解析失败率估计 **10-20%**

**没有健壮的解析和校验逻辑 = 系统必然崩溃**。

### 🟠 高风险问题（Phase 0必须解决）

#### 4. 双Timer并发写入数据库冲突

```csharp
_realtimeTimer = new Timer(ProcessRealtimePool, null, 0, 300000);  // 5分钟
_trendTimer = new Timer(ProcessTrendPool, null, 0, 1800000);       // 30分钟
```

**问题**：
- 第30分钟时，两个Timer同时触发
- 同时向 `signals` 表写入数据
- SQLite 在 Windows 上并发写入性能差，可能导致 "database is locked" 错误

**PRD没有任何锁机制或事务隔离策略**。

#### 5. 成本估算过于乐观

PRD估算：**$0.111/天 = $3.33/月**

**这个估算基于以下乐观假设**：
- 实时池 "90%场景不调LLM" → **没有依据**
- 趋势池每批只有5000 tokens → **暴跌时可能10倍以上**
- 不考虑重试成本 → **JSON解析失败需要重试**

**真实场景估算（2024年8月5日闪崩类似）**：

| 场景 | PRD估算 | 极端场景 | 倍数 |
|------|---------|----------|------|
| 实时池调用次数 | 29次/天 | 288次/天 (全触发) | 10x |
| 趋势池tokens | 5000/批 | 50000/批 (新闻爆炸) | 10x |
| 重试成本 | 0 | 20% | +20% |
| **每日成本** | $0.11 | **$2.64** | **24x** |
| **每月成本** | $3.33 | **$79.2** | **24x** |

**用户可能在一天内花掉一个月的预算却毫无感知**。

#### 6. 信号时效性字段语义不清

```sql
timestamp DATETIME NOT NULL,           -- 信号生成时间
collected_at DATETIME NOT NULL,        -- 采集时间 (在raw_data表)
created_at DATETIME NOT NULL,          -- 记录创建时间
expires_at DATETIME,                   -- 信号失效时间
```

**问题矩阵**：

| 问题 | PRD答案 | 正确答案应该是 |
|------|---------|---------------|
| 回测查询用哪个时间？ | timestamp | 应该是 `first_queryable_at`（明确"何时用户可以查询到"）|
| 9:00事件10:00生成的信号，timestamp是？ | 不确定 | 必须是10:00（否则就是未来函数）|
| expires_at由谁更新is_active？ | 没说 | 需要定时任务 |

#### 7. 幻觉防范只是"君子协定"

PRD说：
> 强制附证据链

但Prompt模板只是告诉LLM：
```
7. **可追溯性**：raw_data_ids必须对应输入数据的ID
```

**问题**：
1. LLM完全可以编造不存在的 `raw_data_id`
2. 没有看到解析后验证 `raw_data_ids` 合法性的代码
3. `reason` 字段的内容无法验证是否是幻觉

**这不是技术保障，只是"希望LLM遵守"**。

### 🟡 中风险问题（Phase 1-2优化）

#### 8. 数据源健康检查缺失

```csharp
public interface IDataCollector
{
    Task<List<RawData>> CollectAsync();
    bool IsEnabled();
    // ❌ 没有: Task<bool> HealthCheckAsync();
    // ❌ 没有: RetryPolicy GetRetryPolicy();
}
```

**场景**：Binance API维护2小时，系统静默失败，用户不知道，回测时这段时间的信号为空。

#### 9. SignalScorer的历史准确率冷启动问题

```csharp
private double GetCategoryHistoricalAccuracy(string category, string symbol)
{
    var outcomes = _repository.GetOutcomesByCategory(category, symbol, days: 30);
    if (outcomes.Count == 0) return 0.5;  // 默认50%
    ...
}
```

**问题**：新系统上线或新增category时，都是50%准确率；用户看到的"历史准确率82%"可能只基于3条数据。

#### 10. 信号冲突处理缺失

**场景**：
- `funding_extreme` 说做多 (strength = +60)
- `whale_movement` 说做空 (strength = -70)
- `sentiment_shift` 说中性 (strength = 0)

加权后可能得到一个无意义的中间值，用户根本不知道该信什么。

#### 11. DSL函数过多，用户认知负担重

## 📝 Gemini 审查结果（2026-01-01）

### 🔴 致命缺陷（必须修复的数据库问题）

#### 1. 违反第一范式（1NF）的 JSON 数组存储
- **问题**：`intelligence_signals` 表中的 `raw_data_ids` 字段定义为 `TEXT` (JSON数组: `[123, 456]`)。
- **后果**：
  - **无法关联**：无法通过 SQL `JOIN` 查询信号对应的原始数据。
  - **无法索引**：无法快速反查原始数据生成的信号。
  - **数据完整性丧失**：删除原始数据后无法级联处理，造成悬空引用。
- **✅ 修复方案**：创建关联表 `intelligence_signal_sources`。
  ```sql
  CREATE TABLE intelligence_signal_sources (
      signal_id INTEGER NOT NULL,
      raw_data_id INTEGER NOT NULL,
      PRIMARY KEY (signal_id, raw_data_id),
      FOREIGN KEY (signal_id) REFERENCES intelligence_signals(id) ON DELETE CASCADE,
      FOREIGN KEY (raw_data_id) REFERENCES intelligence_raw_data(id)
  );
  ```

#### 2. 浮点数精度陷阱
- **问题**：使用 `DECIMAL(10,2)` 存储 `Strength` 和 `Confidence`。SQLite 的 `DECIMAL` 实际上是 `REAL` 或 `TEXT`。
- **后果**：等于比较（如 `strength == 50.0`）可能因精度问题失效。
- **✅ 修复方案**：
  - `Strength` (-100 到 +100) 改为 `INTEGER`。
  - `Confidence` (0.00-1.00) 建议存储为 `INTEGER` (0-100)。

#### 3. SQLite 并发写冲突
- **问题**：`Realtime` 和 `Trend` 两个 Timer 并行运行，可能同时写入。
- **后果**：默认模式下 SQLite 是文件锁，长事务会导致 `database is locked` 异常。
- **✅ 修复方案**：必须开启 **WAL (Write-Ahead Logging) 模式**。
  ```sql
  PRAGMA journal_mode = WAL;
  PRAGMA synchronous = NORMAL;
  ```

### 🟡 高风险问题（查询性能隐患）

#### 4. DSL 高频查询直连数据库
- **问题**：策略回测或实盘时，`GetIntelligenceStrength` 每秒可能被调用多次，直接查库。
- **后果**：TPS 爆炸，IO 占满，严重影响回测速度和实盘响应。
- **✅ 修复方案**：**应用层缓存（L1 Cache）**。
  - `IntelligenceService` 维护内存缓存（ConcurrentDictionary）。
  - 写时更新 DB 和缓存。
  - DSL 查询**只读内存**。
  - 回测开始时预热加载所需数据。

### 🟡 中风险问题（存储与质量）

#### 5. JSON 存储空间浪费
- **问题**：`content` 字段存储完整 API 响应 JSON。
- **建议**：仅存储必要字段，或在应用层 GZip 压缩后存入 `BLOB`。

#### 6. 归档策略缺失
- **问题**：`signals` 表永久保留，数年后会导致单表过大。
- **建议**：每年生成归档库（如 `intelligence_archive_2025.db`），主库保持轻量。

#### 7. 数据清洗机制缺失
- **问题**：依赖 URL 或 ID 去重不可靠。
- **建议**：引入内容哈希 (`content_hash`) 和布隆过滤器进行高效去重。

### 🛠️ 工程实施建议

#### 索引优化
针对查询模式，必须补充以下索引：
1. **DSL查询优化**：
   ```sql
   CREATE INDEX idx_signals_lookup ON intelligence_signals (symbol, category, timestamp DESC);
   ```
2. **去重查询优化**：
   ```sql
   CREATE INDEX idx_raw_source_collected ON intelligence_raw_data (source, collected_at);
   ```
3. **清理查询优化**：
   ```sql
   CREATE INDEX idx_raw_processed ON intelligence_raw_data (processed, collected_at);
   ```

#### 事务一致性
raw_data 处理生成 signals 必须在事务中完成：
```csharp
using var transaction = db.BeginTransaction();
try {
    // 处理逻辑...
    transaction.Commit();
} catch {
    transaction.Rollback();
}
```

### 总结
这份 PRD 的业务逻辑闭环设计良好，但数据层存在 **SQLite并发锁**、**JSON关联查询** 和 **DSL查询性能** 三大硬伤。如果不修复，系统上线后将在高并发场景下迅速崩溃。建议在 Phase 0 阶段优先完成数据库 Schema 的修正和 WAL 模式的配置。
